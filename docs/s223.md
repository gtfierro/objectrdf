# Authoring 223P models

The 223 package (`objectrdf.s223`) adds enumeration constants, automatic
fixed-medium connection points, and solver-backed connection compilation to
the core authoring model (see [authoring.md](authoring.md)).

## Enumerations

223's punned `EnumerationKind` hierarchy (media, roles, aspects, domains...)
generates as constants, not classes:

```python
from objectrdf.s223 import enums

enums.Fluid_Air                       # s223:Fluid-Air
enums.Water_ChilledWater.is_a(enums.Fluid_Water)   # True — hierarchy-aware
enums.Substance_Medium.Mix.Fluid.Air  # hierarchical access, same object
```

Flat names mirror the standard's local names (`Fluid-Air` → `Fluid_Air`) and
are the statically-typed surface; attribute chains exist for exploration.
Enum-valued properties (`has_medium`, `has_role`, `has_domain`) accept these
constants and range-check against the hierarchy.

The constant is the ontology's named individual. It is never instantiated,
even when RDF also declares the same IRI as a class (OWL punning):

```python
assert enums.Substance_Medium.Mix.Fluid.Air is enums.Fluid_Air
fan = Fan("sf", has_medium=[enums.Fluid_Air])
```

Use the punned constant directly wherever a generated enum property expects
it. WaTr follows the same rule and exposes its own additions alongside the
imported S223 hierarchy through `objectrdf.watr.enums`. New project-specific
media or substances belong in an ontology extension; compiling that extension
is what gives them stable IRIs, hierarchy checks, and generated constants.

## Connection points exist because the shapes say so

Connection-point requirements are compiled from SHACL. Concrete points remain
deferred until resolution, so the authored model stays concise:

```python
fan = Fan("sf")
list(fan.has_connection_point)  # []
resolved = model.resolve()
list(resolved["sf"].has_connection_point)  # sf-in + sf-out, both Fluid-Air
```

Slots whose medium is unconstrained or has several allowed media stay lazy.
They are created in a resolved snapshot once the surrounding graph supplies
enough information.

Alternative layouts expressed with `sh:and`, `sh:or`, or `sh:xone` remain as
recursive metadata. The compiler sends their cardinalities, point classes,
and medium domains to Z3 rather than prematurely flattening a branch.

## Connecting things

```python
handle = connect(chiller, pump)        # records an intention
connect(pump_a, pump_b, medium=enums.Water_ChilledWater)
connect(a, b, connection=SpecialPipe)  # constrain the Connection class

report = model.check()                 # solve without materializing
resolved = model.resolve()             # immutable compiled snapshot
conn = resolved.connection(handle)
```

Use `connect()` instead of `>>` when you need to retain or later refine the
intention. `a >> b` returns `b` for chaining; it does not return a handle.

Handles are stable authored objects and can carry connection properties before
resolution:

```python
handle.label = "CHW supply"
handle.has_role.add(enums.Role_Supply)

# Collection assignment replaces all staged roles.
handle.has_role = [enums.Role_Supply, enums.Role_Return]
```

Multi-valued generated properties expose `.add()`, `.remove()`, `.clear()`,
iteration, and membership testing. Assignment follows the generated entity
API and therefore takes an iterable; use `.add(role)` rather than assigning a
bare enum. Scalar generated properties use ordinary assignment. `assign()`
remains an escape hatch for a property declared only by a custom Connection
subclass that the handle cannot discover yet.

`graph()`, `save()`, and `validate()` resolve automatically. The authored
model is never populated with derived points or connections; these exist only
in the snapshot. Any authored edit invalidates the cached snapshot.

## How Z3 resolution works

Connections may remain incomplete while authoring. For each connected
component, the compiler gives Z3 finite-domain variables for active
ConnectionPoints, point classes, selected endpoints, flow media, and
Connection subclasses. It adds hard constraints compiled from SHACL
cardinality and `and`/`or`/`xone` shapes, permitted-media domains, connected
endpoints, and authored facts. Independent components are solved and cached
separately.

After satisfying those constraints, Z3 minimizes a media-affinity penalty.
Two active ports on the same entity prefer the same assignment only when
their permitted-media domains overlap. This is a plausibility ranking, not a
rule that the equipment physically preserves medium. A valid assignment may
use different inlet and outlet media when other constraints support it.

`model.check()` is the non-throwing checkpoint:

```python
report = model.check()
if report.status == "underconstrained":
    for issue in report.issues:
        print(issue.message, issue.labels)
elif report.status == "unsatisfiable":
    print(report.issues[0].labels)  # authored unsatisfiable core
```

Do not use only `if report`: an underconstrained report is satisfiable and
therefore truthy. Test `report.complete` when a unique compiled graph is
required. `resolve()`, `graph()`, `save()`, and `validate()` are strict:
ambiguity raises `AmbiguousModelError`, and inconsistency raises
`UnsatisfiableModelError`.

## Giving the solver media hints

Hints are ordinary authored facts, so they may be added in any order before
resolution. Prefer the narrowest fact you actually know:

```python
# Constrain an intention when it is created.
primary = connect(pump_a, pump_b, medium=enums.Water_ChilledWater)

# Or refine another stable handle later. This invalidates cached resolution.
secondary = connect(pump_b, pump_c)
secondary.medium = enums.Fluid_Water

# A known physical port also selects compatible SHACL layouts.
water_in = InletConnectionPoint(
    "coil-water-in",
    has_medium=enums.Fluid_Water,
    is_connection_point_of=coil,
)
```

Named ports are the concise form when the point needs stable identity but its
remaining facts should still be solved:

```python
feed_in = exchanger.port("feed-in", direction="in")
feed_out = exchanger.port("feed-out", direction="out")
feed_in.pair(feed_out)

connect(source, feed_in)
product = connect(feed_out, tank)
```

`pair()` compiles to a Z3 medium-equality constraint and materializes the
bidirectional `s223:pairedConnectionPoint` relation. An explicit medium on
either mate therefore propagates through the internal pairing. Ports also
accept `medium=` and a mutable `.medium`; their `.roles` are copied to the
materialized connection point.

Solver decisions are inspectable:

```python
explanation = model.resolve().explain(product)
print(explanation.medium)
print(explanation.medium_reason)
print(*explanation.evidence, sep="\n")
```

The reason distinguishes an explicit connection, explicit port, paired-port
propagation, a uniquely determining ontology constraint, and the affinity
preference.

A neighboring constrained device is also a hint: a `Chiller` establishes
`Fluid_Water`. Because water is permitted at both pump ports, assigning water
to the outlet scores better than an otherwise unsupported oil or refrigerant
assignment. The enum hierarchy participates in compatibility, so
`Water_ChilledWater.is_a(Fluid_Water)` is accepted. Broad domains such as
WaTr's `Mix_Fluid` remain open to a more specific adjacent or explicit value.

If neither endpoint nor its connected component constrains a medium—an
isolated pump-to-pump connection, for example—the solver reports ambiguity
instead of guessing. Staged generated properties such as `handle.has_role`
annotate the resulting Connection; they do not affect medium solving. Use
`handle.medium` or `medium=` for that constraint.

One resolved intention produces the full 223 pattern — points on both sides,
a `Connection` of the right class, media everywhere, and both directions of
every inverse (`isConnectionPointOf`, `connectsAt`/`connectsThrough`):

```turtle
:oad s223:hasConnectionPoint :oad-out .
:oad-out s223:hasMedium s223:Fluid-Air ; s223:connectsThrough :oad--sf .
:oad--sf a s223:Duct ; s223:hasMedium s223:Fluid-Air ;
         s223:connectsAt :oad-out, :sf-in .
```

The solver enforces:

- `sh:minCount`/`sh:maxCount` and recursive `and`/`or`/`xone` constraints;
- compatible outlet/inlet classes and point capacity;
- permitted-media domains, explicit `medium=`, and domain-derived affinity;
- the Connection class comes from the medium (air → `Duct`, water/gas/oil →
  `Pipe`), unless constrained with `connection=`.

An impossible model raises `UnsatisfiableModelError` with an authored
constraint core. More than one observable solution raises
`AmbiguousModelError`; add a medium, point, layout, or connection-class
constraint and resolve again. This strict ambiguity rule is intentional:
partial models may remain undecided while authoring, but serialization must
not silently select one valid interpretation.

## Containment

```python
with PhysicalSpace("mech-room"):
    zone = DomainSpace("zone-1", has_domain=enums.Domain_HVAC)  # encloses
    fan = Fan("sf")                                # hasPhysicalLocation
```

Space×space nests via `s223:contains` — exposed as the `contains_` attribute
(trailing underscore: `contains()` is the containment *method*, which is the
intended API anyway). Helper entities the negotiator creates never attach to
open `with` scopes.

## Systems and boundaries

The system scope collects equipment created inside it. Resolution derives
boundary connection points from connections that cross the member set:

```python
with model.system("high-pressure-stage") as stage:
    pump_1 = Pump("high-pressure-pump")
    pump_2 = Pump("booster-pump")
    pump_1 >> pump_2

source >> pump_1
pump_2 >> product
resolved = model.resolve()
system = resolved[stage.entity.name]
```

The authored `System` has `hasMember`; the snapshot also has
`hasBoundaryConnectionPoint` for the first inlet and final outlet.

## Required properties and the cycle rule

SHACL `minCount 1` becomes a required constructor argument — except where two
classes require each other (a Junction requires a ConnectionPoint; every
ConnectionPoint requires its Connectable — no construction order could
satisfy both). The compiler detects such cycles and demotes the *container*
side to validate-time, keeping the pointed-at side (a connection point still
demands its owner and medium up front):

```python
DomainSpace("z")                          # TypeError: has_domain required
j = Junction("j", has_medium=enums.Fluid_Water)   # OK; CPs via negotiation
```

## Validation (with inference)

Generated packages bundle the exact graph used at compilation.
`model.validate()` loads those local shapes and runs shifty — SHACL Core
*plus* the SHACL-AF rules that carry 223's
normative semantics — mapping results back to your objects:

```
info: sf-out (OutletConnectionPoint) [connectsThrough]: `ConnectionPoint`
      ... probably needs an association with a `Connection` ...
```

A negotiated model produces no violations; dangling boundary connection
points (the outside-air inlet of the first damper, say) surface as
info-severity notices, which don't fail `report.ok`.

`model.compile()` is the production checkpoint: it resolves and validates by
default, returning the immutable snapshot or raising `ValidationError`.
Pass `validate=False` only for deliberate partial-model or diagnostic work.
